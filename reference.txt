13. Technical provenance

1. What this establishes

The recovered Ferrum 2.0.5 host protocol provides a basis for building an independent MCU board behind a compatible CP2102N USB-to-UART adapter. The MCU supplies the board behavior: discovery responses, metadata, status, acknowledgements and command execution. The adapter supplies the USB/UART transport. A bare adapter does not perform those board functions.

Recorded result: the original controller machine code accepted reconstructed discovery exchanges in offline emulation. Six discovery cases and eight role/status cases passed in the saved results, with Windows services and transport callbacks mocked. Forty serializer examples also matched isolated execution of the original serializer. These are existing research results, not newly performed hardware tests.

Compatibility claim: an MCU can be connected to implement the documented protocol and attempt operation through Ferrum's driver without Ferrum's own PCB. Successful end-to-end operation on an independent MCU has not been demonstrated by the supplied evidence. It is therefore not established that an implementation will pass every Ferrum check.

In the traced discovery routine, the board-number and firmware-version fields are stored rather than compared against a fixed secret. This is a finding about discovery acceptance, not proof that authentication, licensing, updates or every other Ferrum component is unrestricted. CRC protects frame integrity; it is not cryptographic authentication.

This reference includes every recovered entry in the supplied serial, DHZ, KMNet and board-wire inventories. It is not a complete specification of every Ferrum API, every argument or the entire custom IOCTL protocol. Unresolved fields remain explicitly unresolved.

Online checks in the desktop app

A targeted follow-up static review traced the three direct callers of the desktop app's shared HTTP request routine at 0x140093EB0. All three construct update requests to https://update.xferrum.dev/:

latest.json at 0x14108AF60: retrieves the latest version record and parses version/hash information.

versions.json at 0x14108B800: retrieves the version list.

versions/{major}.{minor}.{patch}.msi at 0x140093230: constructs a versioned installer download URL.

These paths check HTTP status 200 and handle request/response failures. The examined callers do not append board serial numbers, licence keys or authentication tokens, and no remote genuine-board approval requirement was identified in them. Their direct call sites were cross-checked against the executable bytes. Generic TLS certificate/authentication strings in bundled networking libraries are not evidence of Ferrum account or hardware authentication.

Conclusion for the inspected app: update-server communication is confirmed; online board-authentication or licence enforcement was not found. This is a bounded static result for Ferrum 2.0.5, not a live network capture or proof that every indirect path, firmware component, server behavior or future version lacks additional checks. Local driver discovery, selection and liveness requirements still apply.

2. Connecting an MCU and what it can do

Application / Ferrum UI
        |
Ferrum host interfaces and controller driver
        |
Ferrum CP210x filter + Silicon Labs serial driver
        |
USB <--> CP2102N <-- UART --> your MCU
                                  |
                       your implemented device behavior

The analyzed INF attaches the Ferrum CP210x filter to USB\VID_10C4&PID_EA60. Matching that USB ID attaches a transport; it does not complete board discovery. The physical CP210x serial port and Ferrum's virtual serial API port are separate interfaces. COM numbers are machine-dependent. A CH343-style friendly name on the virtual port does not make it a physical CH343 adapter or a transparent UART tunnel.

Connect the adapter's TX to the MCU's RX, its RX to the MCU's TX, and a common ground. Confirm the electrical levels, power arrangement and pinout for the actual boards before connection. The MCU UART must support the traced line settings and baud transitions. Do not assume the adapter's USB enumeration proves that data is reaching the MCU.

CP2102N versus CP2102: the recorded hardware work used CP2102N. Ferrum configures 3,000,000 baud and issues request 0x17. Silicon Labs documents this receive-timeout request as CP2102N-only, so the evidence does not establish compatibility with an older CP2102 or every CP210x variant. Silicon Labs AN571, section 5.18.

The MCU can be programmed to:

Answer legacy or framed discovery and report its own board number and firmware version.

Report peripheral status so the driver can select mouse, keyboard or controller command destinations.

Acknowledge traffic and maintain the framed connection's liveness.

Decode mouse movement, wheel, button and lock/mask messages.

Decode keyboard state, key-mask and timed key-action messages.

Decode controller state and the recovered proxy/message families.

Drive the actual downstream hardware or interface needed by the implementation. Any USB HID device/host behavior requires corresponding MCU hardware and firmware; UART messages alone do not supply it.

Those are implementation responsibilities and supported directions for development, not capabilities already demonstrated on a custom board. The original MCU firmware was not analyzed, and complete device-side semantics are not available for every message.

3. Discovery and board acceptance

Framed sequence

The host configures a pending transport. Framed mode 2 starts at 115200 baud; mode 3 starts at 3000000 baud. It sends C3/11.

The host requests a 5 ms delay, then configures 3000000 baud and a shorter receive timeout. Coordinate the MCU's baud transition with the observed request. The emulator does not validate physical timing.

While the host waits in state 3, the MCU supplies C3/12 with 12 | board_number:u32LE | firmware_version:u32LE, correctly framed and checksummed.

The host sends C3/13. The MCU replies with C3/13 while the host waits in state 4.

The driver promotes the transport to its active list, assigns a runtime board ID, and sends AA/35 with a configuration byte and Q=0. The configuration byte's complete device-side meaning remains unresolved.

The reported board number is distinct from the driver-assigned runtime ID. Offline tests accepted metadata pairs (1,2), (0,0) and (0xFFFFFFFF,0xFFFFFFFF); these are synthetic test cases, not recommended production identities. Acceptance in discovery does not establish how later UI or update paths interpret those fields.

Legacy sequence

The host sends 12 0A. The MCU replies 10 followed by the two u32LE metadata words. The host sends 16 0A and configures 3000000 baud. The MCU replies 16. The host sends 16 0A again and promotes the transport. The native receive parser accepts the single-byte 16; its reply does not require the host's newline.

State and timing

States are 0 configure/probe; 1 wait for legacy metadata; 2 wait for legacy confirmation; 3 wait for framed metadata; 4 wait for framed confirmation; 5 promote; 6 terminal/removal handling. Modes rotate 0 → 1 → 2 → 3 → 0; modes 0/1 are legacy and 2/3 framed. Modes 0/2 begin at 115200 and 1/3 at 3000000 baud. Normal wait thresholds are 100 ms. Persistent candidates older than five seconds use a one-second threshold; older nonpersistent candidates may be removed. These are code thresholds, not measured scheduling guarantees.

C3/10 is a restart/reconnect signal in the traced paths, not a successful metadata reply. Premature confirmation did not promote a board in the recorded offline ordering test.

Serial configuration

The initial line-control buffer represents 8N1. The CP210x filter also sends 0x222024, the Silicon Labs vendor-control IOCTL, containing USB request 0x17 with values 2000 normally or 53 on the framed fast path. These correspond to receive-timeout values in microseconds. Ferrum's traced setup header differs from the printed AN571 table in request-type/length details; acceptance of that exact request must be verified on the target adapter. This setting is separate from the board discovery exchange.

4. Selection, status and liveness

An active connection must also become the selected destination for its intended command family. The traced mouse and controller paths return without sending when no matching active selected target exists. A successful write to the virtual serial port therefore does not prove a command reached the MCU.

AA/22 body:
22 | FLAG | VID:u16LE | PID:u16LE | LA LB LC LD |
A[LA] | B[LB] | C[LC] | D[LD] | Q

LA..LD are byte lengths. Even-length string data is decoded as UTF-16LE. FLAG is parsed as a boolean, but its full device-side meaning and the separate semantic names of all four strings remain unresolved. The VID/PID fields describe the reported peripheral; they are not automatically the adapter's USB descriptor values.

The driver consults its configured device_type_cache: role 0 Mouse, 1 Keyboard, 2 MouseKeyboardCombo, 3 Controller, 4 Other. The role is a host-side classification, not a role byte placed in FLAG. Without a matching cached role, selection falls back to Mouse if that slot is empty, then Keyboard if empty, otherwise Other. Existing selected targets affect the result. Report truthful capabilities and configure the intended role; discovery alone does not select every destination.

The framed active timer sends AA/21 with Q=1 and requests a 500 ms interval. Missed responses accumulate; a count greater than two causes removal/requeue, and send failures also affect handling. The raw acknowledgement is 96 | Q | (Q XOR FF). A valid acknowledgement cleared the pending/missed fields in the recorded original-code tests. Received AA messages cause a corresponding 96 acknowledgement before subtype processing.

An MCU should service periodic queries, report current status, handle the initial configuration and execute its advertised commands. A protocol acknowledgement is not proof that a mouse, keyboard or controller action actually occurred. The legacy path skips the framed heartbeat logic examined here; it still requires protocol-compatible command behavior.

5. Framing and checked example packets

Frame(H, body) = H | COBS(body | CRC16_LE(body)) | 00
H = C3, AA or D7
CRC polynomial = 0x1021; initial = 0xFFFF
No reflection; no final XOR; exclude the outer byte H
AA includes its trailing one-byte Q inside the CRC-covered body

CRC bytes are appended before COBS encoding. Legacy packets and the raw 96 acknowledgement do not use this wrapper. These reconstructed examples use synthetic metadata; they are not live board captures.

Variable fields

AA/31: N is the UTF-16LE byte count, even and at most 254; the serializer caps output at 127 UTF-16 code units. The trailing Q belongs to the body.

D7/53 and /54: duration is unsigned microseconds, u32LE, saturating at 0xFFFFFFFF.

D7/57 and /58: a controller block starts with flags. Bits 0..5 mark six optional 16-bit little-endian fields, emitted in increasing bit order. Bit 6 introduces a three-byte little-endian mask and three-byte masked state; only the low 18 mask bits are used. D7/57 has a prefix byte before the block.

D7/62: prefix, then up to eight chunks. Each chunk's flags encode X width in bits 0..1 and Y width in bits 2..3 (0, 1 or 2 bytes); bits 4 and 5 include one-byte fields A and B. Nonzero X/Y use signed 8-bit where possible, otherwise signed 16-bit little-endian. There is no separate chunk-count byte. Complete meaning of the prefix and A/B remains unresolved.

C3/16: opaque bytes; firmware contents and behavior were not analyzed.

Correction to earlier notes: promotion sends AA/35 with Q=0. A valid AA/21 example with Q=0 is not evidence that the host sends it during initial discovery. AA/21 with Q=1 is verified in the timer path.

11. Other driver interfaces and unresolved coverage

The later inventory identifies controller custom IOCTLs 0x22E000 and 0x22E005 at handler 0x180019160. The former reaches a tag/record parser; the latter is described as connect-by-ID against a driver-owned connection table, with a deferred status completion. The supplied inventories do not establish a complete public buffer schema or client implementation for these operations.

The virtual serial driver also has a serial IOCTL dispatcher. Silicon Labs transport IOCTL 0x222024 is separate from the Ferrum application command families. These surfaces are included to avoid presenting the serial/network lists as a complete inventory of all application-accessible behavior.

No conclusion about universal security, absence of vulnerabilities, generic CP2102 compatibility or MCU firmware support follows from these inventories. The later notes' correction that the connection-engine worker makes no direct WSK calls also means its address alone should not be presented as a complete socket API specification.

12. What must be demonstrated on the custom board

Transport: verify the exact adapter variant, driver attachment, 8N1 settings, requested baud changes and USB control-request completion. Capture actual UART traffic in both directions.

Discovery: observe the complete request, metadata and confirmation sequence on a wired MCU. Check that the driver promotes the transport and assigns a runtime board ID.

Selection: send accurate AA/22 status and confirm that the intended mouse, keyboard or controller destination is selected.

Liveness: keep the framed connection active over repeated timer periods, including realistic processing load; verify disconnect/reconnect and missed-response handling.

Actions: for each advertised command family, verify the host request, actual board-wire message, MCU processing and resulting downstream effect. Test local-only API queries separately.

Coverage: identify and test any additional UI, update, firmware or application checks required by the intended workflow before making a broader compatibility claim.

The existing live adapter evidence shows successful USB OUT transfers and discovery-related activity with no connected MCU. It does not show completed board authentication, physical UART delivery, command execution or a functioning PCB replacement.

“Ferrum 2.0.5's recovered host protocol can be implemented by an MCU connected through a compatible CP2102N adapter. Offline tests exercised discovery, role selection and acknowledgement handling in the original controller code. Live compatibility with an independent MCU, and passage of every Ferrum check, remain to be demonstrated.”
